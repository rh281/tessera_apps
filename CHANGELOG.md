# Changelog

All notable changes to `tessera_apps`. Versions follow [semantic versioning](https://semver.org); a version number is never reused on PyPI.

## 0.2.0 (2026-10-26)

Every embedding is now read through [geotessera](https://github.com/ucam-eo/geotessera) 0.11, the University of Cambridge client, pointed at the dClimate v1.1 store. At the same snapshot every app writes the same output files as 0.1.0, byte for byte, all but the report, and takes longer to do it. In three of the four apps, changing a run's reference or other validation inputs no longer reads the store again. The real validation references and a real restoration site planned for this release could not be reached from the build environment, so the validation numbers and the restore demos are as in 0.1.0.

### Added

- **A hosted demo page** in [demo/](https://github.com/rh281/tessera_apps/tree/main/demo), with a Dockerfile, neither of which is part of the wheel or the sdist: a Streamlit page that shows the five bundled demos' precomputed outputs and runs the wildfire recovery trajectory of a clicked pixel from the one 2.56 km chunk that holds it (live, 48,444,831 bytes in 3.57 s for the default years, nothing when the chunk is cached). Inside the Caldor AOI at the demo's years the click takes the precomputed Caldor run's threshold and unburned reference, so its burned verdict and recovery index are that run's; elsewhere it applies the app's rules, and the app's warnings, to the chunk alone. See the [README](https://github.com/rh281/tessera_apps/blob/main/README.md#hosted-demo).

### Changed

- **The reader goes through geotessera.** `geotessera>=0.11,<0.12` is a new dependency. With it the lock (`requirements-lock.txt`) gains 36 packages (geotessera 0.11.0, dask, folium, contextily, scikit-image, obstore, aiohttp and others), and no existing pin moved. `TesseraReader.open` opens `GeoTesseraZarr(store_url="s3://tessera-embeddings/v1.1/dclimate.icechunk")`, always with that explicit URL. Zone discovery, the published years and every chunk read come from geotessera, and nothing is dequantised on the way. The reader's public API is unchanged. At snapshot `RC6FS07ZB0T76EXT8XRG` the four demos, the two negative stands and a second wetland run wrote output files byte-identical to 0.1.0's (only the reports differ: timings, digests, byte counts and the new fields), and all 201 numbers in [docs/checkpoints.md](https://github.com/rh281/tessera_apps/blob/main/docs/checkpoints.md) that those outputs carry reproduce (0.2.0 checkpoint A).
- **The dataset is checked before any chunk is read.** When geotessera does not name the store `1.1-dclimate`, or the snapshot read holds another model than the one geotessera reports, the run stops with `DatasetMismatchError` and exit code 2, naming the dataset it found.
- **Reports record geotessera and the store.** `provenance.libraries.geotessera` is geotessera's version and is never null again. The `provenance.store` block now has `backend` `geotessera` (was `icechunk`), geotessera's `url` (was `store_url`), `dataset`, `model_version` and `build_version`, and the snapshot read. When the snapshot read holds another build than the head of `main`, `build_version` is the snapshot's and `head_build_version` keeps geotessera's. `tessera-apps info` prints the same fields. The geotessera version is part of every run's arguments digest, so a run made with another geotessera runs again.
- **Snapshot pinning** (`--snapshot`, `TesseraReader.open(snapshot_id=...)`) goes through geotessera's public `IcechunkStore`, because `GeoTesseraZarr` 0.11 cannot pin one (Known limitations, below). An unpinned run reads the head of `main` as it stands when the run opens, and records that snapshot.
- **Wall time.** Bytes read are the same as 0.1.0's to within 0.01 percent, but the demos take 5 to 82 percent longer. Against 0.1.0 in the same session (0.2.0 checkpoint A): Caldor 725 s against 484 s, Rondonia 85 s against 81 s, Everglades 71 s against 48 s, Itapebi 33 s against 18 s and Jaru 44 s against 25 s. Most of the extra time is CPU in geotessera's merged zone view.
- **`bytes_read`** counts chunk payload bytes, shard indexes included, and no longer the `zarr.json` metadata documents, which Icechunk serves from the snapshot it already holds.
- **Memory.** Embeddings are read in strips of whole chunk rows, with at most four reads at once (the environment variable `TESSERA_APPS_EMBEDDING_READS` sets the limit). The `deforest` and `wetland` memory estimates rose to cover the new read path: 1.94 GB for the Rondonia demo and 2.02 GB for the Everglades demo, against measured peaks of 1.92 GB each (0.2.0 checkpoint A).
- **Snapshots older than `B6AFRJGX5XQC0A716PA0`** register the grid at the pixel centre, so geotessera serves a north group's bottom row from neither hemisphere. A read of that row is now refused rather than returned as no data; 0.1.0 read it. The current snapshots are unaffected.
- **`TesseraReader.from_store`** copies the store it is given into a local Icechunk repository in a temporary directory, removed at exit, and reads the copy through geotessera, as `open` reads the published store.
- **Changing only the validation reads no chunk** (`wildfire`, `deforest` and `wetland`). The validation inputs, listed in the [README](https://github.com/rh281/tessera_apps/blob/main/README.md#command-line), are no longer part of a run's arguments digest. The report records them as `validation_params`, and their own digest as `validation_digest`. A rerun that adds, changes or removes one of them, with everything else the same, redoes only the validation, from the outputs on disk. 0.1.0 already did this when only `--validate` was added, when the reference had failed to load, or when the validation file had gone missing. What is new is that a reference file, `--severity`, `--severity-min-class` and `--fire-name` (wildfire) and `--reference-source`, `--reference-classes`, `--gmw-version` and `--seed-buffer-m` (wetland) no longer rerun the whole app. The redo rewrites `<app>_validation.json`, redraws the preview (its reference outline is part of the validation) and rewrites the report, whose `validation_redone` block records the redo; the map, the tables and the other files stay as they are, byte for byte. When the new reference cannot be loaded, the redo removes the earlier validation file and records why, as a full run with those arguments would, and the same command then skips until the reference loads. Live, at snapshot `RC6FS07ZB0T76EXT8XRG`, adding `--validate` to a finished Rondonia run read 0 chunk bytes in 31.2 s, against 1,550,387,529 bytes for the run that made the outputs. 0.1.0 too read no chunk when `--validate` was added; what is new there is the preview, redrawn identical to checkpoint A's full run, with the same scores. A rerun that asks for no validation at all skips and keeps the last validation file, whose inputs the report names. In 0.1.0 a rerun that dropped `--reference`, `--severity` or `--fire-name` (wildfire), `--reference` (deforest) or `--reference`, `--reference-source`, `--reference-classes`, `--gmw-version` or `--seed-buffer-m` (wetland) reran the app in full and removed the validation file; only dropping `--validate` alone skipped. `restore` still reads the store again (Known limitations). The `wildfire` summary also records `distance_histogram`, from which a redo redraws the preview. In the API, `export.outputs_current` takes a `validation_digest` (a validating check without one raises `ValueError`), and `export.validation_args_digest` is new.
- **The validation numbers still use the 0.1.0 stand-ins: none uses a real reference yet.** Scoring against the real references (NIFC perimeters, MTBS severity, Global Mangrove Watch, EFFIS) was planned for this release. Their hosts (NIFC, MTBS, Zenodo and JAXA for GMW, EFFIS) still refuse connections from the build environment, and no substitute was taken. The stand-ins that still stand are a Hansen 2021 loss outline for the NIFC Caldor perimeter, a Sentinel-2 dNBR proxy for MTBS, and the WorldCover mangrove class for GMW.
- **The restore demos are still the synthetic `itapebi` and `jaru`; no real site was added.** USFS FACTS, Restor, Plant-for-the-Planet and Global Forest Watch all refuse connections from the build environment. The Global Forest Watch data lake answers, but it is requester-pays, and the package never needs AWS credentials. The owner supplied 25 plots, all planted in 2025, but the store ends in 2025, so they have at most one post-planting year, and the verdict needs at least two. The plots are not in the repository.
- **`notebooks/00_retrieval.ipynb` is new**: the community retrieval notebook, committed with its outputs, for newcomers to read before the four app notebooks. It reads a point, a box and a list of points, first through geotessera and then from the store directly, in about two minutes (0.2.0 checkpoint D). Its section 9 land cover example is a marked template with placeholder labels and computes no accuracy.

### Fixed

- **`restore`, with one post-planting year:** the "insufficient years" verdict suggested lowering `--min-post-years`, whose floor is 2. It now says to wait for more years (3477cab).
- **A validation redone from the outputs on disk** (in 0.1.0, when `--validate` was added to a run that had not validated, or after a reference that had failed to load) left the preview without the reference outline that a full validating run draws. The redo now redraws the preview, byte-identical to a full run's.
- **`deforest`, after adding `--validate` to a finished run:** the validation was redone from the outputs on disk against Hansen, but `summary.hansen.validation` stayed `false`. The redo now sets it, as a full validating run does.
- **Adding `--validate` to a finished run when the reference could not be loaded** (`wildfire`, `deforest` and `wetland`) skipped, and the report recorded neither the error nor the warning that a full run records. The redo now records both, and the same command then skips until the reference loads.
- **The command's summary after a validation redo** printed the cost of the run that wrote the outputs as if the redo had read it. It now prints both: the earlier run's cost, and "The validation redo read 0.00 GB".

### Known limitations

- **No validation number uses a real reference yet.** NIFC, EFFIS, MTBS, GMW (Zenodo and JAXA) and USFS still could not be reached from the build environment. The NIFC, EFFIS, GMW and USFS FACTS loaders are therefore tested offline only, and the validation numbers in [docs/checkpoints.md](https://github.com/rh281/tessera_apps/blob/main/docs/checkpoints.md) use the stand-ins named there and above. The Caldor demo AOI is derived from Hansen loss for the same reason and should be redrawn from the NIFC perimeter where NIFC can be reached.
- **The Caldor severity map is a Sentinel-2 dNBR proxy** made by `scripts/make_caldor_dnbr.py`, not MTBS. The burned mask's IoU of 0.813 against moderate or worse burn is likely optimistic against real MTBS, since the proxy and the embeddings both come from Sentinel-2.
- **The restore demo sites are synthetic.** No public planting polygon could be reached from the build environment, for 0.1.0 or for 0.2.0, so `itapebi` and `jaru` were located from GLAD canopy height, Hansen, WorldCover and Sentinel-2 imagery. Their files say so, and `scripts/check_restore_demos.py` recomputes the evidence.
- **Each memory estimate rests on one measured run.** The `wildfire` estimate no longer runs low: 4.76 GB for Caldor against a peak of 4.21 GB under 0.2.0 (0.1.0 peaked at 5.38 GB in the same session). The `deforest` and `wetland` estimates, 1.94 and 2.02 GB, sit 1 and 5 percent above their peaks of 1.92 GB. All are from 0.2.0 checkpoint A.
- **Reads are slower than in 0.1.0:** 5 to 82 percent more wall time for the demos, and 187 to 355 s against 61 to 70 s for checkpoint 1's bare one-year read of Caldor, 4.00 GB (0.2.0 checkpoint A). The drafted upstream issue asks geotessera for a faster read path.
- **Snapshot pinning works around `GeoTesseraZarr`.** In geotessera 0.11, `GeoTesseraZarr` has no snapshot or branch argument, takes the plain Zarr path when given a store object, and cannot take a pre-built `IcechunkStore`. So the reads go through geotessera's public `IcechunkStore` class, which `GeoTesseraZarr` uses inside, at the snapshot asked for, and `GeoTesseraZarr` only identifies the store. An issue asking geotessera for snapshot and branch arguments, a store hook and a faster read is drafted in [docs/geotessera-upstream-issue.md](https://github.com/rh281/tessera_apps/blob/main/docs/geotessera-upstream-issue.md), not yet filed. Once geotessera has them, the reads move onto `GeoTesseraZarr` itself.
- **The store's head moves often.** The build saw five different heads between 2026-10-14 and 2026-10-23. An unpinned run records the snapshot it read, but runs compared across days need `--snapshot`.
- **Adding or changing a validation input on a finished `restore` run still reads the store again**, because its canopy check fills columns of the summary table and a panel of the preview. In `wildfire`, `deforest` and `wetland` it reads no chunk. Across a UTM zone seam, a redone validation may score a few seam pixels differently from a full run, as its validation file says.
- **Notebooks 01 to 04 keep the outputs 0.1.0 printed when it ran them.** Their result files and scores are the same under 0.2.0 (0.2.0 checkpoint A), but the version they print, the bytes-read note, the wall times (0.2.0 takes 5 to 82 percent longer on the demos, checkpoint A) and the `deforest` and `wetland` memory estimates are 0.1.0's: 1.51 and 1.58 GB, where 0.2.0 estimates 1.94 and 2.02 GB. Only notebook 00 was run with 0.2.0.

## 0.1.0 (2026-10-21)

The first release: four climate applications on the TESSERA v1.1 global embeddings, read anonymously from the dClimate Icechunk store. No AWS account or credentials are needed.

### Added

- **Four apps, each a `tessera-apps` command and a Python function** (`tessera_apps.apps.run_wildfire`, `run_deforest`, `run_wetland`, `run_restore`):
  - `wildfire`: the burn scar between two years (cosine distance, an Otsu threshold with a bimodality check and a fallback) and each burned pixel's recovery in every later year, calibrated against land that did not burn. Validation against NIFC perimeters, any `--reference` outline, or a burn severity map in MTBS dnbr6 classes (`--severity`).
  - `deforest`: forest in two years from a logistic regression trained on Hansen labels sampled in a ring outside the AOI (or on your own `--labels` CSV), and the forest that became something else. Validation against Hansen loss over the same window.
  - `wetland`: where else a wetland type is, given a few seed points or polygons, and how its extent moved; the threshold comes from seed scores held out by location. Validation against ESA WorldCover or Global Mangrove Watch.
  - `restore`: whether a restoration site diverges from a matched control ring, judged against 200 site-sized placebos, with a null test (control against control), progress toward a mature target stand and a GLAD canopy height check.
- **One command line shape for all four:** `--aoi`, `--year-a`, `--year-b`, `--out`, `--validate`, `--force`, `--snapshot`, `--i-know-this-is-large` and `--strict-validate`; exit code 2, with the reason, for anything that stops a run before it reads (including a store that cannot be opened) and 3 for a strict validation failure; idempotent reruns. Each run writes a Cloud Optimized GeoTIFF, parquet and csv tables, a preview PNG, a report JSON with full provenance and, with `--validate`, a validation JSON. `tessera-apps info` opens the store and prints its snapshot and a zone's published years; `tessera-apps --version` prints the version.
- **The store reader** (`tessera_apps.io`): zone planning for any AOI, a check of every year against the zone's `years_complete` before any chunk is read, streaming of large AOIs in chunk-aligned blocks, batched point reads, radar regime flags, a count of the bytes read, and an optional on-disk chunk cache (`tessera_apps.cache`).
- **Metrics and export** (`tessera_apps.metrics`, `tessera_apps.export`): exact cosine maps on int8, trajectories, Otsu, mask cleaning, PCA false colour with a basis shared across years; COG writing with a zone mosaic, tables, previews and provenance records.
- **Reference data loaders** (`tessera_apps.validate`): NIFC perimeters, EFFIS burnt areas, Hansen Global Forest Change, ESA WorldCover, Global Mangrove Watch, GLAD annual tree canopy height, the Natural Earth coastline and USFS FACTS reforestation, with binary and multi-class scores. Downloads are cached under `~/.cache/tessera_apps/reference/`.
- **Demos bundled in the wheel:** `caldor` (wildfire), `rondonia` (deforest), `everglades` with 12 seed polygons (wetland), and the restore sites `itapebi` and `jaru`, each with a target stand and a negative stand. Pass the name to `--aoi`.
- **Notebooks** 01 to 04, one per app, committed with their executed outputs.
- **Packaging:** Apache-2.0 licence file, `py.typed`, PEP 639 licence metadata, and a release workflow that publishes to PyPI with trusted publishing after the full check, a dist check and a smoke test of the wheel.

### Known limitations

- **The restore demo sites are synthetic.** No public planting polygon could be reached from the build environment, so `itapebi` and `jaru` were located from GLAD canopy height, Hansen, WorldCover and Sentinel-2 imagery. Their files say so, and `scripts/check_restore_demos.py` recomputes the evidence.
- **NIFC, EFFIS, MTBS, GMW and USFS could not be reached from the build environment.** The NIFC, EFFIS, GMW and USFS FACTS loaders are therefore tested offline only, and the validation numbers in [docs/checkpoints.md](https://github.com/rh281/tessera_apps/blob/main/docs/checkpoints.md) use the stand-ins named there: a Hansen 2021 loss outline for the NIFC Caldor perimeter, a Sentinel-2 dNBR proxy for MTBS, and the WorldCover mangrove class for GMW. The Caldor demo AOI is derived from Hansen loss for the same reason and should be redrawn from the NIFC perimeter where NIFC can be reached.
- **The Caldor severity map is a Sentinel-2 dNBR proxy** made by `scripts/make_caldor_dnbr.py`, not MTBS. The burned mask's IoU of 0.813 against moderate or worse burn is likely optimistic against real MTBS, since the proxy and the embeddings both come from Sentinel-2.
- **The wildfire memory estimate is 8 to 10 percent low on Caldor:** 4.76 GB estimated against measured peaks of 5.15 to 5.27 GB.
- **Two items of the build brief are not in this release.** `notebooks/00_retrieval.ipynb` (a copy of the companion notebook `TESSERA_community_applications.ipynb`) is missing because that notebook was never available to the build ([docs/prebuild-survey.md](https://github.com/rh281/tessera_apps/blob/main/docs/prebuild-survey.md)). And the package reads the Icechunk store directly, without `geotessera` (survey B2: before 0.11 it silently reads the legacy v1 model), so the `geotessera` entry the brief asks for in each report's `libraries` is null unless that package happens to be installed, and it never shapes a result.
- **Adding a validation input to a finished run re-reads every chunk.** For example, adding `--severity` or a `--reference` file to a finished Caldor run reads all 23 GB again. Only a rerun after the reference failed to load redoes just the validation, from the outputs on disk (wildfire, deforest and wetland).
